Workloads & Scheduling

15%

Start here — this is the vocabulary every other domain assumes. Master creating and mutating workloads fast, because half of every exam question begins with "deploy a pod that…"

W-1

Generate everything from --dry-run, never write YAML by hand

Objective: produce a Deployment, a Pod, and a Job as YAML using imperative commands, then edit the manifest — the fastest workflow under exam time pressure.

Steps

# scaffold a deployment manifest instead of typing it
kubectl create deployment web --image=nginx --replicas=3 \
  --dry-run=client -o yaml > web.yaml

# a bare pod
kubectl run tmp --image=busybox --dry-run=client -o yaml \
  --command -- sleep 3600 > pod.yaml

# a job
kubectl create job pi --image=perl:5.34 --dry-run=client -o yaml \
  -- perl -Mbignum=bpi -wle 'print bpi(200)' > job.yaml

kubectl apply -f web.yaml
▸
Why it matters: Nobody passes by writing YAML from scratch — you won't have time. Almost every task lets you generate 90% with --dry-run=client -o yaml and edit the last 10%. Building this reflex first pays off in every later lab.
W-2

Rollouts, history, and rolling back a bad image

Objective: update a Deployment's image, watch the rollout, then roll back after a "bad" deploy.

Steps

kubectl set image deployment/web nginx=nginx:1.27
kubectl rollout status deployment/web
kubectl rollout history deployment/web

# simulate a broken release, then recover
kubectl set image deployment/web nginx=nginx:does-not-exist
kubectl rollout status deployment/web   # hangs — pods ImagePullBackOff
kubectl rollout undo deployment/web
kubectl rollout undo deployment/web --to-revision=1
▸
Why it matters: Rollout and rollback are near-guaranteed exam tasks. Practising the broken path teaches you to recognise ImagePullBackOff instantly and reach for rollout undo — which doubles as a troubleshooting skill.
W-3

Config & Secrets into env vars and volumes

Objective: inject a ConfigMap and a Secret into a pod both ways — as environment variables and as mounted files.

Steps

kubectl create configmap app-cfg --from-literal=COLOR=blue --from-literal=TIER=web
kubectl create secret generic app-sec --from-literal=API_KEY=s3cr3t

# then edit a pod spec to consume them:
#   envFrom: [configMapRef: app-cfg]  /  env: [secretKeyRef: app-sec/API_KEY]
#   volumes: [configMap: app-cfg] mounted at /etc/config
kubectl run consumer --image=busybox --dry-run=client -o yaml \
  --command -- sleep 3600 > consumer.yaml
# edit consumer.yaml to add envFrom + volumeMounts, then apply
kubectl exec consumer -- env | grep COLOR
kubectl exec consumer -- cat /etc/config/COLOR
▸
Why it matters: Tasks routinely say "expose this value as env var X and mount this config at path Y." Knowing both delivery methods — and how to verify each with exec — is what earns full marks instead of half.
W-4

Scheduling control: taints, tolerations, affinity & probes

Objective: force a pod onto a specific node, keep others off it, and add health probes so Kubernetes self-heals.

Steps

# taint node1 so ordinary pods avoid it
kubectl taint nodes node1 tier=critical:NoSchedule
kubectl label nodes node1 disk=ssd

# a pod that tolerates the taint AND requires the ssd node
#   tolerations: [key: tier, value: critical, effect: NoSchedule]
#   nodeSelector: {disk: ssd}   (or nodeAffinity for AND/OR rules)

# add probes to a deployment
kubectl explain pod.spec.containers.livenessProbe   # learn the fields live

# cleanup: remove the taint (note the trailing minus)
kubectl taint nodes node1 tier=critical:NoSchedule-
★
Exam speed: kubectl explain <resource>.<path> is your in-terminal reference — faster than opening the browser for field names like tolerations or periodSeconds.
▸
Why it matters: Placement questions ("schedule this only on nodes labelled X, tolerate taint Y") are common and fiddly. The trailing-minus syntax to remove a taint trips people up — drill it now so it's automatic.

Services & Networking

20%

Connectivity is where abstract concepts become debuggable. Every lab here ends with a curl or a DNS lookup, because the exam wants proof traffic actually flows.

N-1

The three Service types, proven with curl

Objective: expose a deployment as ClusterIP, NodePort, then reach it — and understand what each type actually does.

Steps

kubectl create deployment web --image=nginx --replicas=2
kubectl expose deployment web --port=80 --name=web-cip           # ClusterIP
kubectl expose deployment web --port=80 --type=NodePort --name=web-np

# reach ClusterIP from inside the cluster only
kubectl run t --rm -it --image=busybox --restart=Never -- \
  wget -qO- web-cip

# reach NodePort from a node (get the assigned 3xxxx port)
kubectl get svc web-np
curl <NODE_IP>:<nodePort>
▸
Why it matters: Understanding that ClusterIP is internal-only while NodePort opens a port on every node is the mental model behind half of networking troubleshooting. Testing from a throwaway pod (inside) vs a node (outside) makes the difference concrete.
N-2

NetworkPolicy: default-deny, then allow one path

Objective: lock a namespace to deny-all ingress, then permit traffic only from a labelled client — the canonical NetworkPolicy task.

Steps

kubectl create ns secure
kubectl -n secure run api --image=nginx --labels=app=api --port=80
kubectl -n secure expose pod api --port=80

# 1) default-deny-ingress policy (podSelector: {}, policyTypes: [Ingress])
# 2) allow-from-frontend policy: ingress.from.podSelector app=frontend
kubectl apply -f deny-all.yaml
kubectl apply -f allow-frontend.yaml

# prove it: a non-frontend pod is blocked, a frontend pod gets through
kubectl -n secure run probe --rm -it --image=busybox --restart=Never \
  -- wget -qO- --timeout=3 api          # times out (blocked)
kubectl -n secure run probe --rm -it --image=busybox --restart=Never \
  --labels=app=frontend -- wget -qO- --timeout=3 api   # works
★
This only works because you chose Calico. Flannel silently ignores NetworkPolicy, so the "blocked" test would wrongly succeed. If your policies seem to do nothing, check your CNI first.
▸
Why it matters: NetworkPolicy is one of the highest-value, most-missed networking tasks. The deny-all-then-allow pattern is exactly what's tested, and verifying with two differently-labelled probe pods is how you know you got the selector right.
N-3

Ingress and a peek at the Gateway API

Objective: route two hostnames to two services via an Ingress resource (install an ingress controller first).

Steps

# install the NGINX ingress controller (bare-metal manifest)
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/baremetal/deploy.yaml

kubectl create deployment shop --image=nginx --port=80 && kubectl expose deployment shop --port=80
kubectl create deployment blog --image=nginx --port=80 && kubectl expose deployment blog --port=80

# Ingress: host shop.local -> shop:80, blog.local -> blog:80
kubectl create ingress sites --class=nginx \
  --rule="shop.local/*=shop:80" --rule="blog.local/*=blog:80"
kubectl describe ingress sites
▸
Why it matters: Ingress (host/path routing) appears regularly, and v1.35 has added the Gateway API to the curriculum — same idea, newer resources (Gateway, HTTPRoute). Build the Ingress muscle first, then read the Gateway API docs so the newer resource names aren't a surprise.
N-4

CoreDNS & in-cluster name resolution

Objective: confirm how services resolve by DNS name, and know where to look when they don't.

Steps

kubectl -n kube-system get pods -l k8s-app=kube-dns
kubectl -n kube-system get svc kube-dns

# resolve a service by its FQDN from a test pod
kubectl run dns --rm -it --image=busybox:1.28 --restart=Never -- \
  nslookup web-cip.default.svc.cluster.local

# inspect the DNS config Kubernetes injects into every pod
kubectl exec dns -- cat /etc/resolv.conf
▸
Why it matters: "Service X can't reach service Y" is frequently a DNS problem, not a routing one. Knowing the FQDN pattern <svc>.<ns>.svc.cluster.local and that CoreDNS runs in kube-system turns a vague failure into a five-minute fix.

Storage

10%

The smallest domain, and the most self-contained — you can master it in an afternoon. It's the cheapest 10% on the exam, so don't leave it on the table.

S-1

Static PV → PVC → pod, and watch the binding

Objective: create a hostPath PersistentVolume, claim it, mount it, and observe the Available → Bound lifecycle.

Steps

# PV: 1Gi, accessModes ReadWriteOnce, hostPath /mnt/data
# PVC: request 500Mi RWO  ->  binds to the PV above
kubectl apply -f pv.yaml -f pvc.yaml
kubectl get pv,pvc              # PVC Bound, PV Bound to the claim

# mount the PVC into a pod at /data and write a file
kubectl apply -f pod-with-pvc.yaml
kubectl exec store -- sh -c 'echo hi > /data/test && cat /data/test'
▸
Why it matters: The PV/PVC binding dance — capacity, access mode, and how a claim finds a matching volume — is the conceptual core of the domain. Seeing a PVC go Bound (or stay Pending when nothing matches) is exactly the signal you'll debug on the exam.
S-2

Dynamic provisioning with a StorageClass

Objective: create a PVC that auto-provisions its PV via a StorageClass, and understand reclaim policy.

Steps

kubectl get storageclass                 # is one marked (default)?

# a PVC that names a StorageClass -> provisioner creates the PV for you
kubectl apply -f dynamic-pvc.yaml
kubectl get pvc,pv                        # PV appears automatically

# inspect reclaim policy: Delete vs Retain
kubectl get pv -o custom-columns=NAME:.metadata.name,\
RECLAIM:.spec.persistentVolumeReclaimPolicy,STATUS:.status.phase
★
Lab note: a fresh kubeadm cluster has no default StorageClass. Install one quickly with the local-path-provisioner (Rancher) manifest so this lab has something to provision against.
▸
Why it matters: The difference between static (you create the PV) and dynamic (the StorageClass creates it) provisioning is a favourite exam distinction, and Retain vs Delete reclaim policy decides whether data survives a deleted PVC — a detail tasks explicitly test.

Cluster Architecture, Installation & Configuration

25%

The heavyweight admin domain. These labs are destructive by nature — this is exactly why you snapshotted your VMs. Break, restore, repeat until each one is boring.

C-1

RBAC from scratch: Role, RoleBinding, ServiceAccount

Objective: create a ServiceAccount that can only list pods in one namespace, and prove the boundary with auth can-i.

Steps

kubectl create ns dev
kubectl -n dev create serviceaccount viewer
kubectl -n dev create role pod-reader --verb=get,list --resource=pods
kubectl -n dev create rolebinding viewer-b \
  --role=pod-reader --serviceaccount=dev:viewer

# verify the permission boundary both ways
kubectl -n dev auth can-i list pods --as=system:serviceaccount:dev:viewer   # yes
kubectl -n dev auth can-i delete pods --as=system:serviceaccount:dev:viewer # no
kubectl -n default auth can-i list pods --as=system:serviceaccount:dev:viewer # no
▸
Why it matters: RBAC tasks are common and easy to get subtly wrong (Role vs ClusterRole, verb typos). kubectl auth can-i --as=… lets you self-grade in seconds — the single most useful RBAC verification command, and a huge time-saver on exam day.
C-2

etcd backup and restore

Objective: take an etcd snapshot, then restore the cluster state from it — the single most feared exam task, worth practising until it's routine.

Steps

# on the control plane; paths come from the etcd static pod manifest
sudo ETCDCTL_API=3 etcdctl snapshot save /var/backups/etcd.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

sudo ETCDCTL_API=3 etcdctl snapshot status /var/backups/etcd.db -w table

# restore to a NEW data dir, then point etcd at it
sudo ETCDCTL_API=3 etcdctl snapshot restore /var/backups/etcd.db \
  --data-dir /var/lib/etcd-restore
# edit /etc/kubernetes/manifests/etcd.yaml: hostPath -> /var/lib/etcd-restore
# kubelet restarts the static pod automatically
★
Where the certs live: don't memorise the flag values — read them straight out of /etc/kubernetes/manifests/etcd.yaml. The exam gives you the same file.
▸
Why it matters: etcd restore is high-value and high-panic — many candidates lose points purely to nerves and unfamiliar flags. Doing it five times on a disposable cluster converts panic into procedure. Snapshot your VM right before, so you can retry instantly.
C-3

Upgrade the cluster one minor version

Objective: upgrade the control plane and a worker from v1.34 to v1.35 with kubeadm — the reason you deliberately installed one version behind.

Steps

# --- control plane ---
sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm=1.35.0-*
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.35.0
kubectl drain cp --ignore-daemonsets
sudo apt-get install -y kubelet=1.35.0-* kubectl=1.35.0-*
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon cp

# --- each worker (run kubeadm upgrade node, then kubelet) ---
kubectl drain node1 --ignore-daemonsets
# on node1: apt install kubeadm; kubeadm upgrade node; apt install kubelet; restart
kubectl uncordon node1
▸
Why it matters: The upgrade is a guaranteed, high-weight task with a strict order: kubeadm → control plane → drain → kubelet → uncordon, then repeat per worker. Skipping drain/uncordon or upgrading kubelet before kubeadm loses points. This is why the lab cluster runs v1.34.
C-4

Node lifecycle: drain, cordon, and add a node

Objective: safely evict workloads from a node for maintenance, then bring it back — and regenerate a join command.

Steps

kubectl cordon node2                       # mark unschedulable, leave pods running
kubectl drain node2 --ignore-daemonsets --delete-emptydir-data
# ...do maintenance...
kubectl uncordon node2

# produce a fresh join command for a new worker
sudo kubeadm token create --print-join-command
▸
Why it matters: cordon (stop new pods) vs drain (evict existing ones) is a distinction the exam probes directly, and every upgrade/maintenance task depends on it. Regenerating the join token is the fix for "add this node to the cluster" when the original token has expired.

Troubleshooting

30%

The biggest domain, and the one you drill last — because it recombines everything above. The method never changes: describe → events → logs → fix → verify. These labs deliberately break your cluster so you learn to read the symptoms.

T-1

The universal triage sequence

Objective: internalise one repeatable diagnostic path you run on any failing workload before touching anything.

Steps

kubectl get pods -o wide                 # status + which node
kubectl describe pod <pod>                # Events section = the story
kubectl logs <pod> [-c <container>] [--previous]
kubectl get events --sort-by=.lastTimestamp -A | tail -20
▸
Why it matters: 30% of the exam is time-boxed panic unless you have a reflex. The Events section of describe answers most questions — ImagePullBackOff, FailedScheduling, CrashLoopBackOff all announce themselves there. Run this sequence before forming any theory.
T-2

Break a pod four ways, recognise each on sight

Objective: deliberately create the four failure states you'll be asked to fix, and learn their fingerprints.

Steps

# 1) ImagePullBackOff — bad image name
kubectl run bad1 --image=nginx:nope
# 2) CrashLoopBackOff — process exits immediately
kubectl run bad2 --image=busybox -- /bin/false
# 3) Pending / FailedScheduling — impossible resource request
kubectl run bad3 --image=nginx --overrides='{"spec":{"containers":[{"name":"bad3","image":"nginx","resources":{"requests":{"cpu":"100"}}}]}}'
# 4) CreateContainerConfigError — missing configmap/secret ref

# diagnose each with the T-1 sequence, then fix and confirm Running
kubectl describe pod bad3 | grep -A5 Events
▸
Why it matters: Each state has a distinct cause and fix — image typo, bad command, unschedulable request, missing config. Manufacturing them yourself builds instant pattern recognition, so on exam day you skip straight from symptom to remedy instead of guessing.
T-3

Recover a NotReady node

Objective: break the kubelet on a worker, diagnose from the node itself, and bring it back to Ready.

Steps

# on node1: stop the kubelet to simulate the failure
sudo systemctl stop kubelet
kubectl get nodes                        # node1 -> NotReady

# diagnose ON the node — this is the key habit
sudo systemctl status kubelet
sudo journalctl -u kubelet -n 50 --no-pager
sudo crictl ps                           # is the container runtime alive?

sudo systemctl start kubelet && sudo systemctl enable kubelet
kubectl get nodes -w                      # back to Ready
★
Real exam variants: wrong --kubeconfig path in the kubelet service, a full disk, or a stopped containerd. The diagnostic order is always the same: service status → journalctl → runtime.
▸
Why it matters: Node failures are pure points if you know to SSH to the node and read journalctl -u kubelet. Candidates who only ever use kubectl freeze here — because a dead kubelet is invisible to the API. This lab builds the node-level reflex.
T-4

Break the control plane via a static pod manifest

Objective: introduce a typo into an API-server or scheduler static pod, watch the symptom, and repair it.

Steps

# on cp: edit a control-plane component (e.g. mistype the scheduler image)
sudo vi /etc/kubernetes/manifests/kube-scheduler.yaml
# kubelet auto-applies the change; the scheduler pod fails

kubectl -n kube-system get pods           # kube-scheduler not Running
kubectl -n kube-system describe pod kube-scheduler-cp
# symptom: new pods stay Pending because nothing schedules them

# when kubectl itself is down (broken apiserver), read the runtime directly:
sudo crictl ps -a | grep scheduler
sudo crictl logs <id>

# fix the manifest -> kubelet restarts the static pod automatically
★
Key insight: control-plane components are static pods managed by the kubelet from /etc/kubernetes/manifests — not by the API server. Editing the file is the fix; there's no kubectl apply.
▸
Why it matters: This is the hardest troubleshooting archetype: when the API server or scheduler is broken, kubectl may not help, so you fall back to crictl and the manifest files. Practising it removes the worst exam-day surprise — the moment your usual tool stops responding.
T-5

Debug broken service connectivity end-to-end

Objective: trace why "service returns nothing" from selector to endpoints to DNS — the full networking triage.

Steps

kubectl get svc <svc> -o wide
kubectl get endpoints <svc>               # EMPTY endpoints = selector mismatch
kubectl describe svc <svc>                 # compare selector to pod labels
kubectl get pods --show-labels

# then test resolution + reachability from a throwaway pod
kubectl run t --rm -it --image=busybox:1.28 --restart=Never -- \
  sh -c 'nslookup <svc> ; wget -qO- --timeout=3 <svc>'
✓
An empty endpoints list is the smoking gun: it means the Service's selector matches no pods. Fix the labels, and the endpoints populate instantly.
▸
Why it matters: This lab fuses Networking and Troubleshooting — the two domains that are half the exam. The get endpoints step is the highest-leverage move in networking debugging and the one beginners skip, chasing DNS or firewalls when the real cause is a one-character label typo.
